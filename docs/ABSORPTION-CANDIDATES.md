# 吸收候选清单 —— 逐条待审

> 这份是**待审清单**，不是方案。每条一个编号，可以单独批「要」或「不要」。
> 回批方式：整组批（A 组全要）、逐条批（C1 要、C3 不要）、或改后批（C2 要但要改成 X）。
>
> 收录标准：只收**机制级**的东西——能落到规则、能改变判断、能被复核的。观点、口号、趋势一律不收。

## 2 逐条细节

### A 组 · 规模与成本

这一组打的是「做过头」。它的共同前提：**流程成本必须与后果成本成比例**。一条流程只有在它的成本低于它防止的损失时才是资产；施加在它不保护的场合，它就是纯粹的税。而税不会被取消，只会被绕过。

---

**C1 · 三档路由（轻量 / 标准 / 结构）**

- **来源**：BMAD v7 的对外主张之一就是「the process sizes itself to the work —— 小改动直接进 Build，复杂工作才拿到应有的深度」；marmelab 的「大锤砸核桃」与 Radar 的「instruction bloat」说的是同一件事的反面。
- **机制**：叶合同增加一个档位字段。**轻量档五条件同时满足**才能用：不改行为/公共含义/不变量/效果边界；不引入新依赖或技术栈；允许路径不超过一个文件或纯文档；不触及阻塞判断也不改变复用门结论；能被一次全套验证完整覆盖。**结构档**在改目标、改公共含义、不可逆效果、改授权边界时触发，比标准档多一道方案评审。**不确定就用标准档。**
- **我方现状**：∅ 只有一档，所有改动走完整八步。
- **吸收后**：叶合同多一个字段；轻量档省掉设计树、审阅乙、就绪清单其中三条（每条省掉的都要在事件记录写明理由）；状态机一步都不省。
- **代价**：多一个判定点，有被滥用降级（把该走标准档的塞进轻量档）的风险。制动见 C5。
- **推荐**：**强**。这是整份清单里唯一一条被两个独立生态（BMAD 的产品主张、marmelab 的批评）同时指向的东西。

---

**C2 · appetite：时间盒固定、范围可变**

- **来源**：Shape Up。原文的对比很干净——「估算从设计开始、以数字结束；appetite 从数字开始、以设计结束」。
- **机制**：叶合同里除了体积上限，再加一个**时间预算**（小批 / 大批两档）。超预算时的正确动作是**砍范围**，不是延期。范围是被设计出来的，时间是给定的。
- **我方现状**：∅ 有体积上限（≤36 KB）和返工预算（试几次），**没有任何时间维度**。
- **吸收后**：叶合同加一个字段；超时触发一次显式的取舍决定，而不是「再看看」。
- **代价**：时间盒在 agent 场景更难度量（agent 不需要睡觉，实际用时波动大）。可以退化为「预算的检查次数或轮次」，语义仍是「固定成本、可变范围」。
- **推荐**：**强**。我方现在唯一的刹车是体积，而体积管不住「一个 20 KB 的叶反复改十轮」。

---

**C3 · compare-to-baseline 关闭判据**

- **来源**：Shape Up 第 14 章。原文：不要跟理想比，**跟客户今天的现状比**——「客户今天没有这个功能，是怎么凑合解决的？这个功能消除了什么难用的绕路？」
- **机制**：关闭时回答一句：**这次交付相比现状改善了什么**。不是「是否完美」，是「是否比现状好且可信」。
- **我方现状**：∅ 关闭判据全是内部一致性（验收有证据、审阅完成、验证通过），**没有一条问「这值不值得」**。
- **吸收后**：关闭五选一之前加一句必答，答案进归档记录。
- **代价**：可能被写成一句套话。要约束成「具体改变了谁的哪个动作」。
- **推荐**：宜。它填的是我方的真空——我们非常擅长证明「做完了」，完全不擅长判断「该不该做完」。

---

**C4 · scope hammering 作为显式动作**

- **来源**：Shape Up。「范围像草一样长」，以及「砍范围不是降质量」。
- **机制**：给「砍范围」一个**合法动作**，而不是承认失败。砍掉的东西要落成一条记录（砍了什么、为什么可以砍、以后还要不要）。
- **我方现状**：⊂ 有返工预算和停止条件，可以停，但**没有「有尊严地缩小范围」这条路径**。停 = 异常态，缩小 = 没人提。
- **吸收后**：停止条件旁边加一个兄弟选项：主动缩小 + 记录 + 继续。缩小不占用「试第几次」的预算。
- **代价**：需要一个判定「砍掉的部分不影响结果句」的人。
- **推荐**：宜。它把「停」和「缩」分开，而现在这两件事混在一起，于是团队只会选「硬撑」。

---

**C5 · 连续轻量叶的强制升级**

- **来源**：自审（配合 C1）。
- **机制**：一次会话里连续三个轻量叶，**第四个必须走标准档**。任何一条五条件被证伪，立即降级；轻量叶不能关闭父节点。
- **我方现状**：∅
- **吸收后**：一个计数器和三条硬规则。
- **代价**：几乎没有。
- **推荐**：**强**。没有这条，C1 会被用成「所有事都是小事」。连续三次「小事」本身就是信号：要么你对小事的定义跑偏了，要么这个区域在持续渗问题。

### B 组 · 澄清与需求

这一组打的是「做错事」的源头。前提是：**不确定必须被枚举，不能被感觉**。「我觉得需求挺清楚了」无法被证伪、无法被复核、无法被交接。

---

**C6 · 十类需求扫描表**

- **来源**：spec-kit 的 clarify 命令实测 + 通用澄清理论。spec-kit 那一版是逐类打「清楚 / 部分清楚 / 缺失」。
- **机制**：十类：功能范围与行为、领域与数据模型、交互与流程、非功能质量（含安全与合规）、集成与外部依赖、边角与失败处理、约束与取舍、术语与一致性、完成信号、杂项与占位。每个新需求逐类打标。
- **我方现状**：∅ 完全没有。这是整份清单里最大的单点缺口。
- **吸收后**：新增一份参考文档承载十类表；叶的就绪判定前必须有一份扫描记录。
- **代价**：多一个动作。但它是**唯一能把「我以为清楚了」变成可复核现状**的手段。
- **推荐**：**强**。讽刺的是我们批评 SDD「大锤砸核桃」，自己在澄清上完全没有刹车。

---

**C7 · 三个上限：3 / 5 / 一次一问**

- **来源**：spec-kit clarify 的实测约束。
- **机制**：待澄清标记上限 3（第四个说明叶太大，该拆）；一次会话问题上限 5；**一次只问一个**（一次问五个，对方只会回答最容易回答的那个）。
- **我方现状**：∅
- **吸收后**：三条数字写进参考文档。
- **代价**：几乎没有。
- **推荐**：**强**。数字的意义在于它把「问够了没有」变成可判定的。

---

**C8 · 影响 × 不确定度 排序**

- **来源**：澄清理论，spec-kit 采纳。
- **机制**：先问那些「答案会改变做法」且「现在完全不知道」的。
- **我方现状**：∅
- **吸收后**：一条排序规则。
- **代价**：几乎没有。
- **推荐**：宜。它顺带解决「该先问哪个」的争论——而那个争论通常消耗掉整个澄清预算。

---

**C9 · 假设优先 + 代价句 + 疑问句硬约束**

- **来源**：spec-kit clarify 的问题格式约束，加上一个它做对了的点：**能猜就猜，但猜完必须写下来**。
- **机制**：三条合起来——① 默认动作是猜，猜测进 Assumptions，带一句理由和一句「如果错了会怎样」；② 只有三种情况才允许标待澄清（影响范围或体验 / 多解且导致不同实现 / 没有合理默认值）；③ 问题必须是一个**完整疑问句**，编号放在问号后面。标签式提问（「验收的设备与运行时矩阵（FR-023）」）无效。
- **我方现状**：∅
- **吸收后**：三段规则。
- **代价**：几乎没有。
- **推荐**：宜。第③条尤其值得抄——它防的是「看起来问了其实没问」。

### C 组 · 验收与编号

这一组打的是「不能复核」。核心不是格式，是：**一个不能被短引用的规则，会在每次被引用时漂移一次**。

---

**C10 · 验收项 AC-N 稳定编号**

- **来源**：spec-kit 的 requirement→task 回指 + checklist 的 CHK001 递增。
- **机制**：正负验收检查逐条编号，只增不改，退休保留编号。
- **我方现状**：⊂ 已有 RDY1–RDY13（就绪清单）和 E-01（证据表）先例，**唯独验收项没有编号**。
- **吸收后**：叶合同 §5 加 AC-N。
- **代价**：几乎没有。这是把已有做法推广一格。
- **推荐**：**强**。而且它是 C11 和 C12 的前置。

---

**C11 · 引用纪律：编号 + 短标签，绝不重述**

- **来源**：我方 RDY 已有先例（「引编号加短标签，绝不重述清单原文」），这里只是把它**推广到全部四类编号**。
- **机制**：写「AC3 拒绝空输入」，不写那条检查的完整句子。理由：同一条检查在一份合同、一份审阅报告、一份教训条目里被重述三次，就会变成三个略有不同的版本。
- **我方现状**：⊂ 只有 RDY 一类被约束。
- **吸收后**：一条通则，覆盖任务树 ID、RDY、AC、E。
- **代价**：几乎没有。
- **推荐**：**强**。SDD 生态里 review 负担过重的一个真实机制就在这里：验收写成散文，每条被完整复述一次，于是审阅变成了默写。

---

**C12 · reviewer-owned 的只读评审清单**

- **来源**：spec-kit checklist 模板。原句：勾选表示「这条需求质量准则已被复核并满足」，**不表示实现工作完成**。
- **机制**：一份独立于实现的、由审阅者拥有的需求质量清单；实现阶段对它是**只读门**——扫描、统计、出表，**不得修改标记**。
- **我方现状**：∅ 有审阅关注点，但它是**实现者写的**，没有被审阅者拥有的独立制品。
- **吸收后**：一份可选的评审清单模板 + 一条只读规则。
- **代价**：多一份制品。
- **推荐**：宜。它解决的是「实现者替审阅者划重点」这个结构性偏向。

---

### D 组 · 门禁与授权

这一组打的是「悄悄自证」。前提：**执行者的自我报告在结构上不可信**。

---

**C13 · 不变量违例扫描进门禁**

- **来源**：spec-kit analyze 命令。它的定位是「跨制品一致性分析」，且**严格只读**；章程对它不可协商，冲突自动判为最高严重度，**不允许被稀释、重解释或静默忽略**。
- **机制**：在启动门禁里加一条独立扫描：检查这次工作是否违反任何一条已声明的章程不变量或职责边界。命中即阻塞。
- **我方现状**：∅ 门禁十一条里没有任何一条做这件事。
- **吸收后**：门禁加第十二条。
- **代价**：几乎没有。
- **推荐**：**强**。不变量是我们最强的资产（每一刀都指向失败的边界，而不是功能列表），而它现在是**声明式**的——写在章程里，没有任何机制检查它被遵守。

---

**C14 · 前后置 hook 注册表**

- **来源**：spec-kit 的 extensions 机制：读一份配置文件里的 before/after 钩子，四层规则——enabled 为假则过滤（缺省视为启用）、condition 非空交执行器求值、optional 为真只提示、**optional 为假必须真的调用并等待**。
- **机制**：把「每个命令之前/之后要跑什么额外检查」变成可配置注册表，而不是写死在流程里。
- **我方现状**：∅ 每次跑什么固定写在命令里。
- **吸收后**：一份注册表约定。
- **代价**：多一层间接。对个人项目可能过度。
- **推荐**：宜。它的真价值在 C15 那条语义。

---

**C15 · 「光输出一段文字不算执行」**

- **来源**：同 C14。原文明确：optional 为假时，只输出了一个块**不算执行**，必须真的调用并等待结果。
- **机制**：给「执行」和「描述了执行」之间画一条硬线。
- **我方现状**：∅ 我们没有这个概念，于是 agent 写一句「已运行全套测试」就有机会蒙过去。
- **吸收后**：一条判定规则，适用范围不限于 hook——任何「要求某动作已发生」的门都适用。
- **代价**：几乎没有。
- **推荐**：宜。这是 C13/C33 那类机读门的共同前提。

---

**C16 · Scope Guard：非治理意图不得执行**

- **来源**：spec-kit constitution 命令独有的守卫段：如果输入里包含**与治理无关的独立意图**，而它是实现、生成、重构、构建或部署请求，则**不得执行**，只能提取为「推迟的意图」，在结尾建议后续命令但**不得调用**。
- **机制**：治理命令只做治理。被顺手带进来的实操请求要被识别、登记、留待，不能顺手做掉。
- **我方现状**：⊂ 规则优先级里说了用户指令高于章程，但**没有「这条指令不属于当前命令的职权」这个判断**。
- **吸收后**：给治理类动作加一段守卫。
- **代价**：多一层判断。
- **推荐**：宜。它正打在我们最痛的点上——「顺便」是 agent 越界的主要入口。

---

**C17 · 独立的只读分析命令**

- **来源**：spec-kit analyze：非破坏性的跨制品一致性与质量分析，**严格只读**，只能在任务清单完整产出后跑。
- **机制**：一个只判不改的检查动作，产出结论，不动任何制品。
- **我方现状**：⊂ 有审阅甲/乙，但它们是对着**候选实现**的；没有对着**制品之间**的一致性检查。
- **吸收后**：一个只读扫描动作。
- **代价**：几乎没有。
- **推荐**：宜。它和 C13 是同一台机器的两个视图（C13 查不变量，C17 查制品间矛盾）。

---

### E 组 · 变更与影响面

这一组打的是「无声的扩张」。前提：**范围不会自己守住，它只会被守住。**

---

**C18 · Impact 三段**

- **来源**：OpenSpec 的 proposal 模板有「受影响规格 + 受影响代码」两段；第三段是我方扩展。
- **机制**：每个变更写清三段——影响的规格（章程哪节、路线图哪行）、影响的代码（哪些路径及其当前公共含义）、**影响的治理**（哪些既有记录会因此失真：复用记录、教训条目、已归档叶的结论）。
- **我方现状**：⊂ 变更分诊有四问，但产出只决定「开不开新叶」，没有影响面清单。
- **吸收后**：叶合同或变更记录加一段。
- **代价**：几乎没有。
- **推荐**：**强**。第三段是我方独有的，因为只有我们有治理层——SDD 工具没有这一层，所以它们不会问这个问题，也因此不会有「治理记录悄悄过期」这种失败。

---

**C19 · delta 四动词**

- **来源**：OpenSpec conventions。
- **机制**：需求变更用四个动词表达：新增 / 修改 / 删除 / 改名。且**标题本身是唯一标识符**（归一化只做去空白，**大小写敏感**；同一份里标题重复必须报错）。
- **我方现状**：∅ 变更靠自由文本描述。
- **吸收后**：一套四动词语法 + 标识符规则。
- **代价**：引入一套小语法，需要校验。
- **推荐**：**强**。自由文本描述的变更无法**机械核对**，而不可核对的东西在审阅里只能靠信任。

---

**C20 · 修改写成「完整修改后」而不是 diff**

- **来源**：OpenSpec。原文：修改段写**完整的修改后需求**，不是差异。
- **机制**：这条看着反直觉，但它对 agent 是对的——diff 要求读者在上下文之外做心算，而「修改后的完整形态」可以直接被执行和验证。可以附一句「原为 X」但那是注解，不是主体。
- **我方现状**：∅
- **吸收后**：一条写作规则。
- **代价**：文本变长。
- **推荐**：**强**。这条同时解释了为什么叶合同必须是完整快照（见 C28）。

---

**C21 · 改名必须显式写 FROM / TO**

- **来源**：同 C19。因为标题是标识符，改名不是「改个标题」，是**一次删除加一次新增**，必须显式声明，否则会被读成两个不相干的需求。
- **机制**：改名的 FROM 与 TO 成对出现。
- **我方现状**：∅
- **吸收后**：一条规则。
- **代价**：几乎没有。
- **推荐**：宜。它防的是「需求悄悄换了名字，于是追踪链断了」。

---

### F 组 · 上下文与知识

这一组打的是「每个会话重新教一遍」。它也是外部批评里我们**唯一没有对冲**的那条：brownfield 适用性。

---

**C22 · Discover：从既有代码库抽取隐性标准**

- **来源**：Agent OS v3。它的三段是 Discover（从代码库提取既有模式成标准文档）→ Inject（按需注入）→ Shape（带标准的 shaping 问题）。它把「legacy codebase support」当成首要卖点。
- **机制**：在给既存仓库做第一个叶之前，先做一次「把这里已有的做法写成标准」的动作——不是读文档，是**从代码里抽**。
- **我方现状**：∅ 复用发现门查的是「有没有现成的能力可复用」，不是「这里已经形成了什么做法」。
- **吸收后**：一个可选的准备动作，产出一份标准清单，作为后续叶的必读。
- **代价**：一次性成本不低，且抽出来的东西可能不准。
- **推荐**：宜。这是补我们承认的那个洞（在十万行既存仓库插入一个叶，我们没有明确指引）最直接的一手。

---

**C23 · 上下文三通道分离**

- **来源**：OpenSpec：注入通道（全部制品都进来，是**必需的提示词级输入**）、强制规则通道（按制品类型匹配，强制）、顾问建议通道（只影响操作，不约束制品内容）。三条边界各有明文：制品规则**永远不会**被重标成操作建议；工作流**报告冲突但保留控制值**。
- **机制**：把「喂给模型的东西」和「约束模型的东西」和「建议模型的东西」分成三条通道，各有不同的强制力。
- **我方现状**：∅ 混在一起。
- **吸收后**：一套通道约定。
- **代价**：**高**。这是重构级的改动，会让所有模板重新洗一遍。
- **推荐**：缓。概念正确，但现在吸收会撑大系统。先记着。

---

**C24 · 「为什么当初这样设计」的机器可读档案**

- **来源**：ADR 复兴。触发它的是一个具体事故：agent 看到一个「啰嗦的幂等中间件」，判断它冗余，重构掉了——它不知道那层代码是两年前一次事故之后加的，当时 90 分钟内双重扣款 4,200 人。PR 是绿的，审阅者是新来的，第九天同样的失败模式以更低量回来了。
- **机制**：决策记录进版本控制，**在规划阶段被检索、作为约束喂进计划**。要回答的问题就一句：「为什么原来是这样设计的？」
- **我方现状**：⊂ 有裁定（选了什么—为什么—错了代价是什么）和决策表，但它们是**叶内**的，归档后就沉底了，没有「规划时先查历史决策」这一步。
- **吸收后**：给既有裁定加检索入口，规划阶段先查一遍。
- **代价**：检索质量难保证。
- **推荐**：宜。我们的裁定格式已经比 ADR 更严（多了「错了代价是什么」），缺的只是**回读**。

---

**C25 · 可复用指导抽成 skill，保持主指令精简**

- **来源**：Radar Vol 34 的实测解法。有团队把可复用指导抽成 skills，以保持指令精简，缓解 instruction bloat → context rot。
- **机制**：主指令只留**每次都需要的**；成体系的、按需的、只在特定场景才用的，抽成独立单元按需加载。
- **我方现状**：⊂ 已经有 skill 形态，但没有成文的「什么该留在主指令里」的判据。
- **吸收后**：一条判据 + 一次体检测试。
- **代价**：几乎没有。
- **推荐**：宜。这条不是新增能力，是**给我们已有的能力配一条使用规则**。

---

### G 组 · 归档与收尾

这一组打的是「收尾靠自觉」。

---

**C26 · 归档前逐条列出未完成项，默认「否」**

- **来源**：OpenSpec archive 的真实行为：把未完成的任务逐条列出，提示确认，**默认是不继续（为了安全）**；确认时必须列出「将新建哪些规格、将更新哪些规格」及源路径。
- **机制**：收尾是一个**默认否定**的确认动作，而且要先把「还有什么没做」摆在面前。
- **我方现状**：∅ 关闭是五选一，但没有「把未完成项逐条摆出来」这一步。
- **吸收后**：关闭前加一次显式清点。
- **代价**：几乎没有。
- **推荐**：**强**。默认值是这套系统里最强的机制——我们的默认值是「未授权」，同理关闭的默认值应该是「不关」。

---

**C27 · 归档目标已存在就报错，不覆盖**

- **来源**：同 OpenSpec archive。
- **机制**：目标已存在 → 报错，不覆盖。
- **我方现状**：∅
- **吸收后**：一条规则。
- **代价**：几乎没有。
- **推荐**：宜。静默覆盖是「不可逆且无记录」的典型。

---

**C28 · 完整快照 vs 增量引用的边界成文**

- **来源**：自审，配合 C20。
- **机制**：叶合同是**完整快照**（关闭后要在任意未来时刻被独立读通）；但**允许对已在必读集里的来源写增量**——唯一硬约束是：**任何叶特有的字段不得用引用代替**（结果句、允许路径、验收、返工预算、任何非标准停止条件）。
- **我方现状**：⊂ 有一条「绝不用引用代替叶特有字段」，但没有把「什么时候该写全、什么时候可以写增量」讲成通则。
- **吸收后**：一段边界说明。
- **代价**：几乎没有。
- **推荐**：宜。它把一条散落的规则升成一条原理，顺带解释了 C20。

---

### H 组 · 验证与证据

**C29 · 检查必须能移动退出码** —— 我方已有等价条款（检查必须能因实现错误而失败，打印但不影响退出码的违规只是日志行不是门）。**≡ 不需要动。**

**C30 · 自验证必须从原始物重算** —— 我方已有等价条款（重读自己要认证的字段，最多证明文件没被改）。**≡ 不需要动。**

---

**C31 · negative control：失败模式必须是预期的失败模式**

- **来源**：自审扩展。
- **机制**：一条检查因为它自己的 bug 而失败，和因为它发现了问题而失败，**看起来一样**。所以在认可一条检查的失败之前，必须先确认它失败的原因是我们预期的那个原因。分不清的时候，这条检查的结论也不能用。
- **我方现状**：∅ 有「必须能移动退出码」，但没有「移动的原因必须对」。
- **吸收后**：一条判据。
- **代价**：几乎没有。
- **推荐**：宜。它是 C29 的必要补丁——能失败还不够，得**因为对的原因失败**。

---

**C32 · 「QA 只管边角」的验收范围原则**

- **来源**：Shape Up 第 14 章。原文大意：QA 是给边角用的——主路径已经被逐段集成验证过了，QA 要做的是找出那些在环节之间漏掉的、以及边角状态下的问题。
- **机制**：明确验收的分工：主路径靠逐段集成时的证据，终验只负责**环节之间与边角**。这样验收不会变成「重跑一遍所有东西」，也不会变成「抽几个看看」。
- **我方现状**：∅ 三套验证（叶内、全套、集成后）说了跑什么，没说**各自负责发现什么**。
- **吸收后**：给每层验证写一句「这层负责发现什么」。
- **代价**：几乎没有。
- **推荐**：宜。它把「验证」从动作清单变成分工。

---

### I 组 · 机读面

**C33 · 校验器的结构化输出** —— 来源：spec-kit / OpenSpec CLI 全线支持 JSON 输出。机制：校验结果可被程序消费而不只是被人读。我方现状 ∅。**推荐：宜**。它是我方校验器从「能跑」到「能被 agent 用」的分界线。

**C34 · 批量校验** —— 来源：OpenSpec 的批量校验命令。机制：一次校验全部制品，而不是一个一个来。我方现状 ∅。**推荐：宜**。

**C35 · 运行时重读配置而不是缓存** —— 来源：OpenSpec instructions 每次调用都重新读解析根，返回当前快照。机制：配置在**调用时**求值，不是启动时锁定。我方现状 ∅。**推荐：缓**。语义正确，但对我方当前规模是过度设计。

### J 组 · 建议不吸收

列出来是因为你可能不同意，每条给一句为什么我判否。

**N1 · 并行任务标注（spec-kit 的并行标记）** —— 我方是无锁串行，靠「状态只有一个说法」换正确性。加并行标注会立刻要求租约、冲突合并、三方对账，收益远小于代价。**否。**

**N2 · spec 作为代码的唯一来源** —— Tessl 自己已经转向，不再对外主张这条。而且它会把我方拖进 MDD 的老坑：抽象层级尴尬，既不够抽象到能推理，又不够具体到能执行。**否。**

**N3 · 完全无阶段约束的连续动作流（Actions, not phases）** —— 「依赖是使能，不是必须」这句话对探索是对的，对交付是错的。我们的七态状态机不是装饰，它是授权的时间轴。**否。**

**N4 · 无记录的思考回合** —— 留白属于草稿阶段，不属于执行阶段。想清楚的过程可以很乱，但一旦进入工作流，每一步都要有痕迹——否则「为什么选了这个」这个信息在第一次需要它的时候就已经不存在了。**否。**

**N5 · 多工作集 / 多仓并联** —— 多根会把「唯一事实源」变成「哪一根」。**否。**

**N6 · 目录式无审查的能力安装** —— 发现与安装分离，安装永远是独立的显式授权动作。**否。**

## 3 需要你注意的三件事

**第一，C1 和 C5 是一对，不能只批一个。** 只有路由没有刹车，等于给滥用开了门；只有刹车没有路由，刹车没有意义。

**第二，原来说「C6 是性价比最高的一条」这句作废。** 复核发现澄清机制不是空的（见 §5.2 错 1），C6 反而要先做映射才谈得上补。真正性价比最高的是 C11 + C19 + C20 这一组：它们与现有条款不冲突，只把已经写对的做法推广到全部制品上。

**第三，C19–C21 三条是一套，拆开用会互相打架。** 四动词、写全不写 diff、改名显式，三者共用同一个前提：**标题是标识符，不是序号**。

## 5 复核：首版哪里判错了

### 5.0 一句话

这份清单是**按「别人有什么」逐条扫出来的，不是按「本项目缺什么」扫出来的**。方向反了，所以出现了两类错：把已有的东西当成空白（重复造轮子），把有不同答案的地方当成空白（会造出互相矛盾的规则）。复核用 `grep` + `read` 把每条的「我方现状」按仓库原文核了一遍，六处判错。

### 5.1 复核方法

- 逐条 `grep` 关键词（clarif / question / assumption / invariant / default / scope），再 `read` 命中的文件取上下文；
- 只用**原文 + 行号**下判断，不接受「我记得模板里有」这种转述；
- 判 ∅（我方没有）必须有「搜过且没搜到」的证据，否则降为「未核实」。本轮六处错里有五处本该有这一步。

### 5.2 六处判错

#### 错 1 — 澄清不是空白，是一套**不同答案**（C6 / C7 / C8 / C9）

我原来判「澄清机制我方完全没有」。实际有三处：

- `portable/references/design-interview.md` 全 50 行，是首次项目访谈和**每一个叶设计**的清单；:9-42 分六簇（意图与合同 / 正常路径 / 负路径与边界 / 状态并发与失败 / 复用效果与授权 / 停止线）；:7 每轮结尾必须重述决策树（已定 / 新解锁 / 仍等决定）；:50 「实施开始时仍有未闭合分支是停止条件，不是脚注」。
- `portable/templates/project-charter.md:192-197` §10 Risks and open decisions，`D-01` 表，四列 `Question / risk | What would settle it | Owner | State`，状态值 `OPEN`。
- `portable/templates/leaf-task.md:244-256` §10 Design tree，frontier 逐题 `Q1…Qn`，每题 `Recommended / Reason / Alternative / Disclosed cost`，闭合条件是所有题已裁定或显式结转，Provider line 记录哪个 provider 跑的。

所以不是缺，是三条**分歧**：

| 候选 | 现有答案（原文） | 关系 |
|---|---|---|
| C6 十类扫描表 | 六簇清单（design-interview.md:9-42） | 各有出入：十类的「非功能质量」「术语一致性」在六簇里没有独立位置；六簇的「停止线」「复用与授权」十类里没有。要先做映射表才知道补哪几条。 |
| C7 一次只问一个 | :3 明文 `ask every currently answerable question in one numbered batch with a recommended answer` | **直接冲突**。要吸就得先改 design-interview.md，否则系统里同时存在两条相反指令 —— 正是 `default-on-policy.md:10-15` 说的最坏情况：下一个 agent 分不清「考虑过并否决」和「从没注意」。 |
| C8 影响×不确定度排序 | 排序原则是 `currently answerable`（按阻塞关系，能答的先答） | **也是冲突**。两种排序对同一批问题给出不同顺序。 |
| C9 假设优先 + 代价句 | `with a recommended answer` + `never let an assumption pass silently` | 已有雏形。缺的只是「假设要落成带理由与代价的记录」，不是从零。 |

**修正**：C6 ∅→⊂/宜，C7 强→缓（改为「改不改现有访谈设计」的决策项），C8 宜→缓（同上），C9 保持宜但性质改为「补记录形态」。

#### 错 2 — 默认值这件事仓库里有一整篇，而且比我写的好（C36）

`portable/references/default-on-policy.md` 全 46 行。:10-15 原文：

> There is no runtime. Every gate is enforced by an agent reading the file that records whether the gate passed. A rule that ships off is therefore not neutral — it is invisible, and the next agent has no way to tell "considered and declined" from "never noticed".

:19-32 给出四要素：① 出厂默认值取保守值，不取常见值也不取便宜值；② 收窄必须具名**并说出排除了什么**（「收窄但没排除任何东西」等于没填）；③ 收窄要留下批准人和日期，写在拥有该策略的文件里，不写在会被归档的 handoff 里；④ 用不到它的场合必须零成本（低风险叶只是记录 `NOT_REQUIRED` 并列出考虑过哪几个 id，不跑审阅）。:3-8 已经装了两个默认开启项：session ledger、Review B 五条 RVB 全 `YES`。

我那条 C36 只说了「对 AI，默认值就是行为的实际决定因素」，顶多覆盖这里的第 ① 条。**把已有且更强的机制当成新发现——这是我自己没做 reuse-first。** 撤销 C36。

#### 错 3 — negative control 已经是硬要求（C31）

`portable/templates/leaf-task.md:116-118`：

> a self-verification recomputes each asserted value from the originals — a check that re-reads the field it certifies proves at most that the file was not edited, and **a tampered copy must fail it**.

「篡改副本必须挂掉」就是 negative control。∅→⊂，降为宜，且实际要做的是核对现有条款覆盖了哪几类失败，而不是新增名词。

#### 错 4 — 三档路由不是纯加法，会和已有的 Mode 维度打架（C1）

`portable/templates/project-charter.md:180-190` §9 Automatic development authorization 已有一整套：`Mode: MANUAL | AUTO_DEV`、授权任务 ID 或范围、允许的自动续跑效果、每叶最大修复轮次、允许的 B 类变更、强制停止条件、有效期或复看日期。其中 :190：

> Automatic continuation never includes a change to the Goal, Non-goals, Invariants, release boundary, sensitive-data policy, public semantic contract, or irreversible external effect.

这一句已经是**结构档触发清单的雏形**。再并列加一套轻量/标准/结构，agent 就同时持有两个「我该走多重的流程」的判据；按 `default-on-policy.md` 的教训，两套判据并存时较松的那套会被当成真正的那套。

**修正**：C1 仍判强，但性质从「新增一维」改成「**把已有的效果授权边界升格成显式档位**」，落地时必须与 §9 合并成一套，不能并列。

#### 错 5 — 运行时重读没有落脚点（C35），另有三条理由写错（C14 / C33 / C34）

`default-on-policy.md:10` 一句就否掉了：**There is no runtime.** 这套件是纯文件合同 + agent 自觉，没有进程缓存配置，也没有「重读」这个动作。判「缓」等于承诺一件不存在的事 → 改 **N/A / 否**。

C14（hook 注册表）、C33（JSON 输出）、C34（批量校验）仍可做，但它们的**理由要重写**：我原来按「可执行」给它们定价，本项目的门禁不是执行器，是 agent 读文件。它们的真实价值是可 `diff`、可机核、让下一轮 agent 不必重新推理——和 C29/C30 属于同一类，属于「可复核性」不属于「自动化」。

#### 错 6 — C13 成立，但边界比我说得窄；C16 的差距只剩一格

- `DEVELOPMENT_CHARTER.md:263-277` 门禁十一条逐条核过，确实没有「逐条核验这一叶触碰了哪条不变量」→ **C13 成立**。
- 但 C16 不是空白：`portable/references/change-triage.md:36` 原文 `If the route is OUT_OF_SCOPE, stop and ask for the new authorization instead of folding the request into the current task.` 已经是「不折叠、停下要授权」。真正缺的只有一步：**把被拒的附带请求记成清单**，而不是直接丢掉。差距从「要不要加 Scope Guard」缩成「丢之前要不要留档」。

### 5.5 这次复核本身留下的教训

1. **判 ∅ 必须有搜索证据。** 六处错里五处是「我记得没有」，一处是「我没打开那个文件」。
2. **拿外部清单当清单，本身就是反 reuse-first。** 本项目有 `reuse-first`、`reduce-reinvention` 两个 provider 和一个复用发现门，我给的建议却没有对自己的项目先跑一遍。
3. **「冲突」比「空白」更危险。** 空白最多是没做；冲突会让 agent 在两条相反指令之间按最省力的一边选，而且不留记录。清单里凡是「对方有、我方有别的」都该单列，不能塞进「吸收」。
