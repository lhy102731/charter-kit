# Charter 2.0 —— 一份完整的治理方案

> 这份文档是**完整版本**，不是补丁清单。它把 Charter Kit 的全部治理思想重写一遍，并把从 SDD 生态两轮审计里该拿的东西**内化进正文**，而不是另起一节说「这里要加一条」。
>
> 它写的是思想与规则，不是实现。所有条款以完整句子的形式给出，可以直接照着说话、照着判断、照着拒绝。
>
> 它不改变任何授权，也不构成对现有叶的批准。落地映射见附录 B。

---

## 序：这份方案要解决什么

AI 编码的真实失败模式，不是「写不出代码」。

代码从来不是瓶颈。瓶颈是四件事，而且它们都发生在代码之外：

1. **做错事** —— 交付了一个没人要的东西，而且从第一天起就没人有权力说停。
2. **做过头** —— 做了很多没人要求的东西，每一项单独看都合理，合起来是一个失控的项目。
3. **悄悄自证** —— agent 说「已完成，测试通过」，而这句话本身既是主张又是证据。
4. **无法交接** —— 三周后没人记得为什么这么设计，于是重做一遍，或者更糟：不敢动。

这四件事有一个共同点：**它们都不是规格问题**。写一份更详细的需求文档，对这四件事一件都不起作用。

所以这套方案的对象不是「要做什么」，而是另外三个问题：

- **谁允许做** —— 授权；
- **做到什么算完** —— 关闭判据；
- **做错了怎么判** —— 处置。

规格管第一个问题的原料，治理管后两个问题以及第一个问题的**权力结构**。这两者的混淆，是 SDD 生态里大部分批评的真正来源：它们把治理问题当成规格问题来解，于是产出了越来越多、越来越长的 markdown，而上面的四个失败模式一个都没动。

**一句话定位**：规格是输入，治理是操作系统。这份方案写的是操作系统。

# 第一篇 第一原则

六条，按不可让渡程度排序。任何一条被违反，其余五条就失去意义。冲突时按序裁决。

## 一、代码是主产物，治理制品是派生品

这一条决定了整套体系的上限和下限。

代码是最终交付物，是唯一会对使用者产生后果的东西。章程、叶合同、roadmap、证据记录全部是**为了让代码正确而产生的治理制品**——它们有存在价值，但没有独立价值。当治理制品开始为了自身完整性而增长时，它已经从工具变成了负担。

推论三条：

- **不生成代码**。治理层描述意图、边界、验收，不描述实现。一旦治理制品开始承载实现细节，它就变成了第二个代码库，而两个代码库必然不同步——这是 MDD（模型驱动开发）三十年前踩过的坑：抽象层级尴尬，既不够抽象到能推理，又不够具体到能执行。
- **治理制品的体积是成本，不是资产**。叶合同有上限，教训层有上限，交接文档有上限。超限时的正确动作是**把内容搬到拥有它的地方**，而不是删掉验收检查来腾位置。
- **治理层的失败判据是「阻碍了代码前进」**，不是「记录不完整」。一个记录完美但让团队三个月没交付一个功能的过程，是失败的过程。

## 二、授权是状态转移的前提，不是氛围

系统的默认值是否定的。

这听起来是小事，它是整套体系里最硬的一条。因为 AI 的根本特性是**它永远愿意干**。你说得含糊，它就选一个合理的方向做了；你没说停，它就一直做；你说「顺便」，它就把顺便也做了。所以在这个环境里，「没有明确禁止」等价于「已授权」，而「已授权」等价于「不受控」。

因此：

- 每一个状态转移都是一个**授权事件**，不是一个时间点。从草稿到批准、从批准到就绪、从就绪到开工，每一次都需要一个具体的、可指认的授权来源。
- **项目批准不批准任何叶**。批的是方向和边界，不是工作量。
- **候选不是授权**。「下一个可以做的是 X」是一句信息，「去做 X」是一个授权，两者之间隔着一次明确的批准。把前者读成后者，是最常见的越界形式。
- **预授权必须是匹配的**，不是笼统的。批了自动开发模式，不等于所有叶都可以自动开工；只有与该叶匹配的那一份预授权才成立。
- **批准有有效期**。条件变了，批准就失效——不是「需要重新考虑」，是失效。

## 三、关闭由证据决定，不由声明决定

执行者的自我报告在结构上不可信。

注意这个措辞：不是「不可靠」，是「不可信」。不可靠是概率问题，多验几次也许能好；不可信是结构问题——执行者的目标函数是「让任务看起来完成了」，而验证者的目标函数是「确认它真的完成了」。这两个函数在数学上不是同一个。所以任何系统如果允许前者给自己发合格证，它验证的就不是完成度，是表达力。

因此证据必须满足三个条件才算证据：

- **它能失败**。一条检查如果无论实现对错都会通过，它就不是检查，是一句日志。判断标准很朴素：**它必须有可能因为实现错误而变成失败**。做不到这一点的东西，写进报告时只能标成「记录」，不能标成「验证」。
- **它从原始物重算**。重读一个字段、复述一段文档、引用一份自己刚写的摘要，最多证明「这个文件没被改过」，不能证明「这件事是对的」。要证明对，得从源头重新算一遍。
- **它在正确的上下文里做出**。见第八篇。

推论：分支提交不是关闭，跑绿了 focused 测试不是关闭，agent 报告不是关闭。它们都是**输入**，不是**判据**。

## 四、复用优先于建造，但「先查有没有」这件事必须先被证明

不重复造轮子是一条人人都同意的原则，也是一条几乎从不被执行的原则——因为它没有可证伪的形式。「我查过了，没有现成的」这句话可以是真的，也可以是零成本的敷衍。

所以它必须被赋予和授权同样的地位：**一个有状态、有证据、可阻塞的门**。

- 复用发现的结果有三种状态：完成、待定、阻塞。待定和阻塞都**不能**授权一个叶开工。
- 覆盖程度是四种事实：搜过、没搜、没权限搜、工具链不通。这四种是**覆盖事实**，不是门状态。把「没搜」写成「没找到」，是把一个未知伪装成一个否定——这是统计上最常见的自欺形式，也是最容易被 agent 顺口做出来的事。
- 范围必须写清在哪一层：工作区与历史、已安装与缓存、已授权的内部资源、官方上游与注册表、已授权的公网。不同层的结论强度不同，混在一起说「查过了」等于什么都没说。
- 被选中的候选必须固定到不可变的版本（具体的提交、标签或包版本）。「最新版」不是一个可以拿来汇报的东西。
- 发现是只读的。查的时候不装、不跑、不克隆、不导入。

豁免是允许的，但豁免不是第四种状态。它是一份**决策证据**：写明哪个叶、批了哪些范围、接受什么限制、谁批的、什么时候失效。没有这五项，豁免只是一句好话。

## 五、事实源唯一，投影必须同步

同一件事只能在两个地方同时存在，前提是它们由同一次改动同时更新。

这不是洁癖，是防止系统的「乐观读取」：当三份记录对同一状态给出三个不同说法时，人（和 agent）会自动选择最有利的那一份。这不是恶意，是本能。所以必须规定：**任何不一致都是阻塞性发现，不是可以在其中挑一个的菜单。**

- 权威源只有一个，其余全部是**投影**，并且必须声明自己是投影。
- 状态在任务记录与路线图上同步迁移，从不单方面前进。
- 任何一次权威变更，必须同时更新它的全部投影。
- 交接、摘要、报告都是派生物。派生物与权威源冲突时，无条件是派生物错。

## 六、不确定必须被枚举，不能被感觉

「我觉得需求挺清楚了」不是一个可以接受的判断，因为它无法被证伪、无法被复核、也无法被交接。

不确定性有两种处理方式，两种都可以，但必须显式选一种：

- **猜**。做有依据的假设，把假设写进 Assumptions。这是默认动作，成本最低。绝大多数「不清楚」其实有一个足够好的默认值。
- **问**。标记为待澄清，带着具体选项去问。

被禁止的只有第三种：**既没说清也没标注，直接实现**。它看起来最有效率，实际上把不确定性从可见的地方挪到了不可见的地方，代价在几周后以返工的形式付清，而且那时候没人记得当初是猜的。

为了让它可执行，不确定必须有**形状**：一张固定的扫描表（见第五篇），十个类别逐类打「清楚 / 部分清楚 / 缺失」。价值不在表本身，在于**漏了什么看得见**。

# 第二篇 核心模型

## 2.1 七个状态，每一个都是一次授权

**草稿** → **批准** → **就绪** → **进行中** → **审阅** → **已验证** → **已关闭**

完整重述每个状态的准入门槛与离开条件：

| 状态 | 进入条件 | 在这一步获得的授权 | 离开条件 |
|---|---|---|---|
| 草稿 | 有一个候选行为 | 无。可以写，不能做 | 合同字段齐全，自评审通过 |
| 批准 | 收到与该叶匹配的明确批准 | **可以为一个具体范围做就绪准备** | 通过就绪清单全部条目 |
| 就绪 | 就绪清单全绿，证据齐全 | **可以改代码** | 实现完成，候选就位 |
| 进行中 | 已开工 | 只允许在允许路径与允许效果内 | 候选可评审 |
| 审阅 | 存在可评审的候选 | 无。审阅者只判，不改 | 审阅结论记录，发现闭环 |
| 已验证 | 集成前的全部验证通过 | **可以集成** | 目标分支集成完成 |
| 已关闭 | 集成后验证通过 | 无。**这就是终点** | — |

四条不可绕过的补充规则：

1. **顺序不可跳**。审阅在验证之前，验证在集成之前，集成在集成后验证之前，集成后验证在关闭之前。把「集成前验证通过」当成「集成后也一定通过」，是最容易发生的一类伪造。
2. **状态在任务记录与路线图同步迁移**。不允许「任务记录已经关了但路线图还显示进行中」。
3. **异常态是显式的**：部分完成、阻塞、工具链阻塞、需要决策、暂停。每一个都必须带原因。**没有「悄悄停在这里」这个选项。**
4. **关闭之前必须有账目对平**。账目对不上又没留下「未启用」的痕迹，就只能关成部分完成并写明原因，不能关成已关闭。

## 2.2 三种授权，各授什么、不授什么

- **项目批准**：授方向、边界、效果范围。**不授**任何叶的工作量。
- **叶批准**：授这一个叶的允许路径、允许效果、验收口径。**不授**它的后续叶。
- **预授权（自动模式）**：授「在已批准的叶集合内按规则推进」。**不授**范围外的任何东西，也不授「条件变化后继续」。

三者共有的性质：**可撤销、有边界、与具体对象绑定**。

## 2.3 四层证据，强度不同不能互相替代

| 层 | 是什么 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 一 | 退出码 | 检查跑了，且它有能力失败 | 检查是否覆盖了该覆盖的 |
| 二 | 原始物重算 | 结论来自源头，不是转述 | 源头本身是否被正确选取 |
| 三 | 独立上下文审阅 | 规格、实现、验收之间没有缝 | 实现是否真的正确（它读的是候选，不是运行结果） |
| 四 | 集成后验证 | 在真实基线上仍然成立 | 后续不会破坏 |

**关闭需要四层齐。** 缺任何一层，都只能关成部分完成。

## 2.4 复用门：三种状态、四种覆盖、五种范围

- 五种范围层次（从强到弱）：工作区与历史 → 已安装与缓存 → 已授权的内部资源 → 官方上游与注册表 → 已授权的公网。
- 四种覆盖事实：搜过 / 没搜 / 没权限搜 / 工具链不通。
- 三种门状态：完成 / 待定 / 阻塞。**只有「完成」能授权就绪**，其余两种要么等，要么走有界豁免。
- 五种候选去向：采纳 / 适配 / 仅作参考 / 新建 / 需要决策。**「需要决策」不是拖延，是一个必须有人回应的状态。**
- 一条时效规则：后续叶不重复全量搜索，只在新的能力、技术栈、边界变化或过期触发时做**定向复查**。复查也是搜索，也要留证。

## 2.5 处置：两条轴，不自动映射

**修复等级**（谁有权修）：

- **A 级**：在合同内，实现者自己修。
- **B 级**：需要预授权，超出合同但仍在批准范围内。
- **C 级**：必须由人决策，涉及目标、范围、公共含义、授权或不可逆效果。

**严重度**（多急）：

- **P0**：交付即有害，立即停。
- **P1**：阻止关闭。
- **P2**：必须排期，不阻止当前叶。
- **P3**：记录在案，不承诺。

**两条轴独立。** 一个 P0 的问题不会因为「它在合同内」就变成可以自己修完继续走；一个 A 级的问题也不会因为「好修」就降低它的严重度。把两者混成一条轴，是最常见的降级手法：先说「这个我自己改一下」，然后这件事就消失了。

## 2.6 裁定：不允许无声的决定

**每一个被发现的岔路口，都要留下走哪一边、为什么、以及错了会付出什么。**

格式是固定的：**决定（Ruling）：选了什么 —— 为什么 —— 如果错了代价是什么**。

规则：

- 只要一次偏离没有被记录成裁定，它就是**一个秘密做出的决定**。秘密决定不算决定，算事故。
- 只有当停止条件被打中时才允许停下来问。没打中停止条件的岔路，自己裁定、写清楚、继续走。
- 停下来问是有成本的：它把工作从一个上下文搬到另一个上下文。所以停下来必须是因为**权限或事实**不够，不能是因为不想承担判断。

# 第三篇 完整的工作循环

从零到一个已关闭的叶，八步。每步写清：做什么、产出什么、什么算过、什么必须停。

## 第一步 立项（无项目时）

1. **读环境**：定位标准工作集，只补缺的，不覆盖已有的。
2. **验依赖**：把要用的能力逐项标为可用 / 缺失 / 未验证 / 有回退，写明影响与动作，落成一份记录。缺必需能力就是阻塞。
3. **访谈**：从一个意图种子开始，把用户与场景、痛点、可观察的目标、非目标、不变量、产品回路、资产、复用范围、效果边界、成功等级、风险、第一个有界行为，全部问出来并记录。种子本身不是需求。
4. **写章程**：目标纠偏、资产盘点、能力地图、授权边界、任务树、自评审。
5. **提交批准包并停**。项目批准不批准叶。

**必须停的信号**：无法证明某个东西在批准范围内；风险等级与授权等级不匹配；有未处理的发现。

## 第二步 建叶

写一份**有界合同**。它的核心不是描述任务，而是**把任务封在一个可以被验证的盒子里**。

必须包含，且不得用引用代替：

- **一条结果句**。一个可观察行为。判断标准：这句话里出现两个「和」就拆开。
- **允许路径与允许效果**。正向白名单 + 负向清单，两者都要有。
- **正负验收检查**。带稳定编号。正向说「应该发生什么」，负向说「什么必须被拒绝或保持不变」、以及「失败的时候留下什么痕迹」。
- **全套验证口径**。不是「跑我这个叶的测试」，是「跑整个套件」。一个叶的文件单独跑绿不是绿。
- **审阅关注点**。点名「规格暗示了但没有检查覆盖」的输入与失败模式，逐条给出钉住它的检查，或者写清为什么跑不了。**「没有发现」也是一个合法的字段值**，但必须写出来，不能留空。
- **停止条件与返工预算**。什么情况下停，允许试几次。
- **允许体积**。上限是硬约束。超了要搬内容，不能删验收。

## 第三步 就绪判定

十三条清单，全部通过才能从批准进到就绪。它的作用是**把开工的决定变成一个可以被别人复核的动作**。

十三条覆盖六类东西：合同本身是否批准且可追溯、前置是否真的关闭、结果与边界是否明确、验收与停止条件是否成对、宿主能力与批准是否到位、复用门是否完成或有界豁免且投影一致。

**引用方式有纪律**：编号加短标签，绝不重述清单原文。重述一次，漂移一次。

## 第四步 实现

- 只在允许路径内改，只产生允许效果。
- 先让检查失败，再让它通过。负向检查永远不删。
- 每一条记录下来的命令，在提交回执之前**重跑一次**。回执上写的是重跑的结果，不是记忆的结果。
- 陈述要么在这次提交里可被核对，要么显式标为「预期」。把预期写成事实，是回执里最严重的错误。

## 第五步 审阅

两个独立的审阅，不是两次同一个审阅。

- **审阅甲**：不持有实现上下文的审阅者，只看合同、规格、候选差异。它判的是覆盖与正确性、范围漂移、测试质量。如果它和实现者在同一个上下文里，那这次审阅记为**降级**，并且必须写明失去了什么。
- **审阅乙**：在确定的高风险条件下触发——安全或鉴权、外部依赖、公共接口或公共含义、高风险或不可逆效果、用户明确要求。同一个叶的审阅乙必须换另一个独立上下文。
- 结论只有三种：需要、不需要（列出考虑过的条件加有界理由）、已豁免（条件命中但没有可用的审阅者，且有用户书面有界豁免）。

## 第六步 验证

在集成之前，对**最终候选**做完整验证。四层证据的前三层在这里齐。

## 第七步 集成

在目标分支上集成。集成后立刻做一次**基线验证**——不是重跑同样的检查，是确认「换了一个基线之后仍然成立」。

## 第八步 关闭

五选一：已关闭 / 部分完成 / 阻塞 / 工具链阻塞 / 需要决策。

**已关闭**的全部门槛：验收有证据、审阅完成、集成前验证通过、目标分支集成完成、集成后验证通过、账目对平（或有未启用的留痕）。缺一只能选部分完成并写明缺什么。

关闭时同时做四件事：归档出向合同（增量编辑，绝不整文件重写）、清活动叶、同步下一个授权状态、镜像到路线图。

**「下一个候选」是信息，「下一个授权」是许可。** 关闭后默认值仍然是「未授权」。

# 第四篇 三档路由 —— 流程成本必须与后果成比例

**这是本版最重要的一条新原则。**

一条流程只有在它的成本低于它防止的损失时才是资产。当一条流程被施加于它不保护的场合，它就变成了纯粹的税。

旧版本的问题不是流程错，是**只有一档**。所有改动都走完整的八步，于是「改一个错别字」和「换掉鉴权模型」付出同样的代价。这个代价不会消失，它会以两种方式转移：

- 人会开始绕过流程（于是最需要它的高风险改动也一起被绕过）；
- 或者人会停止做小改动（于是产品停止生长，而流程看起来一切正常）。

两种结局都是失败。所以必须有档位，而且档位必须有**判定条件**，不能凭感觉。

## 4.1 三个档位

### 一档：轻量（TRIVIAL）

**五个条件必须同时满足**，任何一条不满足立即降级：

1. 不改变任何已批准的行为、公共含义、不变量或效果边界；
2. 不引入新的依赖、版本、技术栈、外部边界；
3. 允许路径不超过一个文件，或者是纯文档；
4. 不触及任何阻塞判断，也不改变复用门的结论；
5. 能被一次全套验证完整覆盖。

**它是什么**：仍然是一个叶，仍然走草稿 → 批准 → 就绪 → 进行中 → 审阅 → 已验证 → 已关闭。速度来自**省掉哪些准备动作**，不是来自跳过状态。

**它省什么**：设计树、审阅乙、就绪清单里的第 9、10、11 条。省掉的每一条都要在事件记录里写明理由。

**它的刹车**：

- 一次会话里连续三个轻量叶，**第四个必须走标准档**。理由是连续三次「小事」是一个信号：你对「小事」的定义已经跑偏了，或者这个区域正在持续渗出问题。
- 一旦发现任何一条五条件不成立，**立即降级**，已经做的工作作为标准叶的输入，不白做。
- 轻量叶**不能关闭一个父节点**。父节点的完成永远需要标准档的证据。

### 二档：标准（STANDARD）

默认档位。完整的八步、十三条就绪清单、两个审阅、四层证据。**当你不确定该用哪一档时，用这一档。** 不确定性本身就是一个降级信号。

### 三档：结构（STRUCTURAL）

触发条件（命中任意一条）：

- 改变目标、非目标或不变量；
- 改变公共含义（对外承诺、接口语义、数据格式）；
- 不可逆或高后果效果（删数据、发外部请求、动钱、动权限）；
- 改变授权边界本身。

**它比标准档多的东西**：一次显式的**方案评审**——先把「做什么、为什么、代价、被拒的替代方案」写清，拿到独立评审，再进标准档。而且它必须有一个明确的反对者角色：有人专门负责说「这条路不对」。

## 4.2 档位的三条元规则

1. **档位由后果决定，不由工作量决定**。「这个改动很小」不是理由——小改动改在鉴权上就是结构档。
2. **升级免费，降级有价**。任何时候都可以往上升；往下降必须写明五条件如何满足。
3. **档位必须写在叶合同里**，和 Mode 在一起。没写档位的叶默认是标准档。

## 4.3 为什么这条原则比它看起来重要

它同时解决了三个此前无解的问题：

- **外部批评里最实的那条**：markdown 太多、流程过重、小改动成本高于收益。那些批评打的是「一档制」，不是治理本身。加了档位，批评落空，而治理强度没降。
- **流程腐化**：任何只有一档的流程，最终都会被绕过。档位让「合规地走捷径」成为可能，从而保护了高风险路径上的合规。
- **brownfield 适用性**：在既存大仓库里，绝大多数工作是小改动。没有轻量档，这套体系在真实项目里就只剩「不敢用」一种用法。

# 第五篇 澄清：把不确定变成一张能勾的表

## 5.1 十类扫描表

每个新需求、每个变更、每个叶之前，逐类打标：**清楚 / 部分清楚 / 缺失**。

| # | 类别 | 要问的 |
|---|---|---|
| 1 | 功能范围与行为 | 核心目标与成功标准？显式的范围外声明？角色区分？ |
| 2 | 领域与数据模型 | 实体与关系？身份与唯一性？生命周期与状态转移？数据量级假设？ |
| 3 | 交互与流程 | 关键路径？错误态、空态、加载态？可达性与本地化？ |
| 4 | 非功能质量 | 性能？可扩展性？可靠性与可用性？可观测性？安全与隐私（鉴权、数据保护、威胁假设）？合规？ |
| 5 | 集成与外部依赖 | 外部服务及其失败模式？导入导出格式？协议与版本假设？ |
| 6 | 边角与失败处理 | 负向场景？限流与节流？冲突解决？ |
| 7 | 约束与取舍 | 技术约束？显式取舍或被拒的替代方案？ |
| 8 | 术语与一致性 | 有没有术语表？该避免的同义词与废弃叫法？ |
| 9 | 完成信号 | 验收是否可测？完成定义是否可量化？ |
| 10 | 杂项与占位 | 遗留的待办？没有量化的形容词（「健壮」「直观」「高性能」）？ |

**价值不在表，在「漏了什么看得见」。** 六类标清楚、四类标缺失，这就是一份可以被复核的现状；「我觉得差不多了」不是。

## 5.2 三个数字和一个排序

- **待澄清标记上限 3**。一个叶如果出现第四个，说明这个叶太大，应该拆。
- **访谈问题上限 5**。一次会话最多问五个问题。
- **一次只问一个**。一次问五个，对方只会回答最容易被回答的那个。
- **排序：影响 × 不确定度**。先解决那些「答案会改变做法」且「现在完全不知道」的。
- 每个问题必须是**二到五个互斥选项**，或者明确限定五个词以内的短答。开放式的长篇追问没有停止条件。
- 问题的写法有硬约束：必须是一个**完整的疑问句**。话题标签、小节标题、需求编号都不是问题。「验收的设备与运行时矩阵（FR-023）」是无效的，它是一个标签；「在哪些设备和运行时上验收？（FR-023）」是有效的。编号只能放在问号后面。

## 5.3 猜是第一选择

**能猜就猜，猜完写下来。** 这是默认动作，因为它的成本最低、可逆性最高。

猜测必须写进 Assumptions，带一句理由和一句「如果错了会怎样」。猜完不写的假设，等于没做的决定。

只有三种情况才允许标待澄清：

- 显著影响功能范围或用户体验；
- 存在多个合理解释，且不同解释导致不同的实现；
- 没有合理默认值可猜。

## 5.4 停止条件

什么时候算澄清够了？

- 五问用完，或者下一个问题不影响做法；
- 十类里没有「缺失」，且剩下的「部分清楚」都有书面假设兜底；
- 你能用一句话说出这个叶的结果，且这句话里不需要「大概」「基本上」「类似」。

**过了这三条还在追问，追的就不是需求，是安全感。**

# 第六篇 编号：一个不能被短引用的规则，会在每次被引用时漂移一次

## 6.1 四种编号

| 类型 | 形态 | 作用 |
|---|---|---|
| 任务树 | 层次 ID（史诗 / 能力 / 切片 / 叶） | 位置与依赖 |
| 就绪项 | RDY 加序号 | 十三条清单的稳定锚 |
| 验收项 | AC 加序号 | 正负检查的稳定锚 |
| 证据项 | E 加序号 | 证据表的稳定锚 |

## 6.2 只增不改

**编号只增不改**。退休的条目保留编号，标注退休日期；新条目取下一个号。**重新编号会静默改变已归档记录的含义**——这是不可接受的，因为归档记录的全部价值就在于它说的和当初说的一致。

## 6.3 引用纪律

引用一律写**编号加短标签**，绝不重述条目原文。

- 写「AC3 拒绝空输入」，不写「第三条负向检查：当输入为空时系统应当拒绝并返回错误」。
- 写「RDY10 复查触发当前」，不写「就绪清单第十条：投影的门状态与复用记录和章程一致且复查触发日期未过期」。

理由很直接：**重述会漂移**。同一个检查在一份叶合同、一份审阅报告、一份教训条目里被重述三次，就会变成三个略有不同的版本，然后没人知道哪个是权威的。编号是唯一不会漂移的东西。

## 6.4 为什么这条是思想问题而不是格式问题

因为**可引用性是复核的前提**。一条无法被短引用的规则，无法在另一个上下文里被检查、被对账、被反驳。它只能被复述，而复述即改写。

SDD 生态里 review 负担过重的一个真实机制就在这里：一叶几十条验收写成散文，每条都被完整复述一遍，于是「审阅」变成了「重读并默写」。

# 第七篇 变更与影响面

## 7.1 三种变更，三条路

| 变更性质 | 路径 |
|---|---|
| 新需求、缺陷、新发现的约束或风险 | 变更分诊四问 → 决定是否新开叶 |
| 范围或事实变化 | 重新过授权，不静默扩张当前叶 |
| 目标或公共含义变化 | 结构档，方案评审先行 |

**四问**：还在目标内吗？影响章程、路线图还是当前叶？引入新能力、依赖、版本、技术栈、风险或外部边界吗？当前授权已经覆盖了吗？

第四个问题是关键。前三个问题的答案都是「是」，第四个可能是「否」——而「否」意味着这件事现在不能做，不管前三个答案多合理。

## 7.2 影响面三段

每个变更必须写清三段：

- **影响的规格**：章程的哪一节、路线图的哪一行；
- **影响的代码**：哪些路径，以及这些路径当前的公共含义；
- **影响的治理**：哪些既存记录会因此失真（复用记录、教训条目、已归档叶的结论）。

第三段是本套件独有的，因为它有治理层——SDD 工具没有这一层，所以它们不需要问这个问题，也因此不会有「治理记录悄悄过期」这种失败。

## 7.3 增量表达的边界

**叶合同是完整快照，不是增量。** 它关闭之后要被归档，并在任意未来时刻被重新读通；一份只有增量的合同，读它必须先有完整上下文，而那个上下文那时已经不存在了。

**但允许对「已在必读集里的来源」写增量。** 规则是：可以引用加差异，**但任何叶特有的字段不得用引用代替**——结果句、允许路径、验收检查、返工预算、任何非标准停止条件，必须写全。因为这些字段一旦变成引用，这个叶就不能独立成立了。

# 第八篇 人机分工

## 8.1 三栏划分

| 栏 | 内容 | 判据 |
|---|---|---|
| **人判** | 价值、授权、边界、取舍、不可逆决定、对外承诺 | 有后果且不可逆 |
| **机器判** | 一致性、格式、可测性、编号唯一性、投影同步、退出码 | 有唯一正确答案且可枚举 |
| **独立上下文判** | 不变量是否被破坏、规格与检查之间有没有缝、范围有没有漂移 | 与实现者目标函数冲突 |

第三栏是这个划分里最有意义的一格。它不是「更重要」，而是**在结构上不能由实现者自己完成**——原因在第一原则第三条已经说明：目标函数不同。

## 8.2 关于「同一个上下文里的自我审阅」

它**不成立**，但不是因为它不诚心。

理由是：审阅的全部价值来自「读的人不知道作者的打算」。一旦审阅者已经知道打算，他就无法判断「只读合同的人能不能看懂」，而这恰恰是审阅要回答的问题。所以同上下文的审阅不是审阅，是**校对**——校对有用，但它是另一种工作，必须如实标名。

## 8.3 什么时候必须换人

- 高风险、物质目标变化、授权变化、用户明确要求；
- 审阅乙的全部五个触发条件；
- 任何「结论会影响是否继续投入」的判断。

# 第九篇 验证哲学

## 9.1 五条

1. **退出码高于输出**。一条检查如果不能影响退出码，它就不是门，是日志行。把它写成门是自欺。
2. **原始物高于转述**。自验证必须从源头重算。重读自己要认证的字段，最多证明文件没被改。
3. **整表高于单文件**。「这个叶的文件单独跑绿」和「套件绿」是两件事，前者的常见成因是别人坏了。
4. **负向检查不可删**。删负向检查是最容易的「修复」，也是最彻底的掩盖。
5. **失败模式必须是预期的失败模式**。一条检查因为它自己的 bug 而失败，和因为它发现了问题而失败，看起来一样。分不清的时候，检查本身的结论也不能用。

## 9.2 关于「测试通过」这句话

它有四种含义，必须区分：

- 检查跑了并通过（第一层证据）；
- 检查在正确的前提下跑了并通过（前提被记录且可核对）；
- 检查覆盖了应该覆盖的东西（需要第三层）；
- 改动在真实基线上仍然成立（第四层）。

**说「测试通过」而不说哪一层，等于什么都没说。** 这是回执写作里最常见的一种含混。

# 第十篇 教训与自省

## 10.1 教训层

一份有界的、建议性的项目知识库。**它是知识，不是门。**

- 进什么：降级、返工、超预算修复、审阅发现、过期豁免。
- 不进什么：一次性的操作失误、没有机制解释的抱怨。
- 一个坑一个条目。零产出是合法的。
- 晋升进套件是用户确认后的手工动作，绝不自动写入。

**为什么它不是门**：因为让史实变成强制项，会让系统越来越难走，最后所有人绕着它走。教训的价值在于被读到，不在于被强制。

## 10.2 流程自省

每两三个叶问一次：

- 产品开发的时间是否仍然高于流程维护的时间？
- 有没有叶是「因为流程要求」才存在的？
- 最近三次降级是不是都发生在同一类地方？

第二条最有诊断价值。「因流程而存在的叶」是最隐蔽的官僚化征兆，它在合法性的外衣下增长。

## 10.3 什么时候该怀疑流程本身

三个信号：

1. 轻量档的连续三个上限经常被打满；
2. 教训层里同一类条目反复出现；
3. 团队开始用「先做完再补记录」的方式工作。

三个里出现任何一个，问题都不在执行，在流程。

# 第十一篇 反模式

每一条写成：**症状 → 机制 → 正确做法**。

**1. 大锤砸核桃**
症状：改一个错别字也走完整八步。
机制：只有一档。
正确：三档路由，由后果决定档位。

**2. 悄悄扩张**
症状：做的时候「顺手」多做了两件相关的事。
机制：没有变更分诊，或分诊的第四问被跳过。
正确：新需求不得静默扩张当前叶；四问全过才动。

**3. 自证合格**
症状：「已完成，测试通过」。
机制：允许执行者给自己发合格证。
正确：四层证据；第三层必须独立上下文。

**4. 假设隐身**
症状：三周后发现有件事当初是猜的，没人知道。
机制：猜了没写。
正确：猜是第一选择，但必须写进 Assumptions 并带代价说明。

**5. 三份记录三个说法**
症状：任务记录说在审阅，路线图说已验证，交接说在实现。
机制：允许乐观读取。
正确：任何不一致都是阻塞发现，不是选一个。

**6. 影子决定**
症状：走了一条和合同不同的路，事后没人记得为什么。
机制：没有裁定纪律。
正确：任何偏离都必须有裁定三要素，否则算事故。

**7. 未搜当没找到**
症状：「我查过了，没有现成的」。
机制：把覆盖事实伪装成门结论。
正确：四种覆盖必须如实标注；「没搜」不能写成「没找到」。

**8. 用体积换通过**
症状：合同超限，删掉两条验收来腾位置。
机制：上限没有配套的搬运规则。
正确：超限时把内容搬到该去的地方，永不删验收。

**9. 审阅变成默写**
症状：审阅者花了大部分时间重读文档。
机制：规则不能被短引用。
正确：稳定编号加只增不改。

**10. 元工作失控**
症状：治理制品比代码长得快。
机制：治理有独立的价值判断。
正确：代码是主产物；治理的失败判据是阻碍了代码前进。

**11. 只在绿地上好用**
症状：新项目很顺，既有仓库插入一个功能处处卡。
机制：流程没有针对既存代码库的路径。
正确：轻量档 + 复用发现的定向复查 + 影响面第三段（治理失真）。

**12. 秘密的降级**
症状：某个 provider 没装，系统自己找了个替代，没人知道。
机制：允许静默回退。
正确：任何降级必须当场显式记录，记在叶里不记在日志里。

# 第十二篇 边界：这套方案不做什么

写清楚不做什么，和写清楚做什么一样重要。

- **不生成代码**。治理层不进入实现，不产生第二个代码库。
- **不做并行**。无锁、无租约、无并发合并。串行是特性不是缺陷——它换来了「状态只有一个说法」。
- **不做无记录的探索**。想清楚的过程可以很乱，但一旦进入工作流，每一步都有痕迹。留白属于草稿阶段，不属于执行阶段。
- **不提供目录式的无审查安装**。发现与安装分离，安装永远是独立的显式授权动作。
- **不做多工作集**。一个项目一个工作集。多根会让「唯一事实源」变成「哪一根」。
- **不替代人的判断**。它做的是让人的判断有位置可放、有证据可依、有记录可查。

# 附录 A：本版确立的十条原则

前六条是第一原则的复述，后四条是本版新增或显著强化的。

1. 代码是主产物，治理是派生品。
2. 授权是状态转移的前提，默认否定。
3. 关闭由证据决定，不由声明决定。
4. 复用优先，且「先查过」必须被证明。
5. 事实源唯一，投影必须同步。
6. 不确定必须被枚举，不能被感觉。
7. **流程成本必须与后果成本成比例**（三档路由）。
8. **不能被短引用的规则，会在每次引用时漂移一次**（编号只增不改）。
9. **执行者的自我报告在结构上不可信**（不是不可靠，是目标函数不同）。
10. **任何偏离都必须留下裁定三要素，否则是秘密决定**。

## 一句话收束

SDD 教给我们的不是「写更多规格」，而是一个反面样本：**当一套方法把「把话说清楚」当成终点，它就会产出越来越多的文档，而真正的四个失败模式——做错事、做过头、悄悄自证、无法交接——一个都不动。**

这套方案的全部设计，都在这四个失败模式上各放一个装置。三档路由防「做过头」，授权与编号防「做错事」，四层证据与独立上下文防「悄悄自证」，裁定、事实源唯一与教训层防「无法交接」。

其余一切，都是这些装置的实现细节。
