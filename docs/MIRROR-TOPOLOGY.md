# Mirror topology and build order

## 摘要（先读这四条）

1. 同一份内容在仓库里存在多份拷贝。改动前先确认哪一份是**手工源**，哪一份是**生成物**。
2. 根目录 `skills/charter-workflow/` 是**生成物**：Codex 构建器会回写它。手工改动会被 `shutil.rmtree` 删掉，不会报错，也不会合并。
3. 但 DSH 构建器把这个生成物当作**输入**。因此构建顺序有意义：先 codex，再 dsh。
4. 验证器能发现不一致，但错误信息常常指着错误的一侧。用下面的表决定该改哪个文件。

## Why this file exists

The kit ships the same governance core to four hosts. To keep each installed
package self-contained, several trees hold byte-identical copies of the same
files. Three of those copies are hand-edited sources, three are generated by
builders, and one tree is both — it is generated by one builder and consumed as
input by another.

Nothing in the build machinery announces which is which. Editing a generated
tree is silently discarded, and the validator's byte-mismatch messages name the
two paths that disagree rather than the path a maintainer should open. This file
is the map. It documents the current behavior; it does not change it.

## Hand-edited sources

| Path | Role |
| --- | --- |
| `portable/` | The semantic source of truth: templates, host prompts, the command, and references. |
| `DEVELOPMENT_CHARTER.md`, `DEPENDENCIES.md`, `dependencies.json`, `scripts/check_dependencies.py`, `scripts/init_project.py` | Canonical root core files. `MIRRORS` in `scripts/validate_kit.py:236` requires each to equal its copy under `skills/charter-workflow/`. |
| `targets/codex/` | Codex adapter source: `.codex-plugin/plugin.json` plus a self-contained `skills/charter-workflow/` tree. |
| `targets/zcode/` | ZCode adapter source: `.zcode-plugin/plugin.json`, `commands/charter-workflow.md`, and its own self-contained `skills/charter-workflow/` tree. |
| `targets/dsh/` | DSH adapter source: `package.json`, `src/`, `build.sh`, `README.md`. It carries no skill tree of its own. |

A file that exists in more than one of these places must be edited in every one
of them in the same change. `SKILL.md` has three hand-edited copies (root and
both target trees); `dependencies.json`, `check_dependencies.py`,
`init_project.py`, and `DEVELOPMENT_CHARTER.md` have four each (root canonical
plus three skill trees).

## The three chains

```text
codex   targets/codex/skills/charter-workflow  ─┐
        targets/codex/.codex-plugin/plugin.json ├─> plugins/charter-kit/ ─┐
        root core files (portable/, scripts/…)  ─┘                        │
                                                     writeback  <─────────┘
                                        root skills/charter-workflow/
                                        root .codex-plugin/plugin.json

zcode   targets/zcode/{.zcode-plugin,commands,skills} ─> plugins/zcode-charter-kit/
        (no writeback)

dsh     root skills/charter-workflow  ─┐
        targets/dsh/                  ─┴─> plugins/dsh-charter-kit/
```

- Codex: `scripts/build_codex_plugin.py` reads `TARGET_SKILL_RELATIVE` (`:19`),
  stages the plugin, then calls `sync_legacy_snapshot` (`:346`, invoked at
  `:434`) which copies the **generated** tree back over root
  `skills/charter-workflow/` and root `.codex-plugin/plugin.json`.
- ZCode: `scripts/build_zcode_plugin.py` reads `targets/zcode/…` (`:25-28`) and
  writes `plugins/zcode-charter-kit/`. It never writes into the repository root.
- DSH: `scripts/build_dsh_plugin.py` reads root `skills/charter-workflow`
  (`:29`, copied at `:301`) together with `targets/dsh/`, and writes
  `plugins/dsh-charter-kit/`.

## Root `skills/charter-workflow/` has two identities

It is Codex's writeback destination and DSH's build input at the same time.

Two consequences follow, and both are silent:

- **Hand edits are deleted, not merged and not reported.** `copy_tree`
  (`scripts/build_codex_plugin.py:204`) calls `shutil.rmtree(destination)` at
  `:210` before copying. A file added or changed under root `skills/` disappears
  at the next `python scripts/build_codex_plugin.py` run with no diagnostic.
- **`--check` does not cover it.** `ensure_check_match` (`:392`) compares a fresh
  stage against `plugins/charter-kit/` only. It never inspects root `skills/`, so
  `build_codex_plugin.py --check` passes while root `skills/` is stale — and DSH
  will package that stale tree.

This also conflicts with the design record. The multi-target design
(`docs/superpowers/specs/2026-09-01-multi-target-distribution-design.md:51`, restated at `:68`)
declares root `.codex-plugin/` and `skills/` to be deprecated legacy snapshots
kept only for compatibility during migration, to be deleted once the marketplace
path stabilizes, and states that maintainers do not edit two sets by hand. The
DSH work then made that deprecated tree load-bearing:
`docs/superpowers/plans/2026-09-01-dsh-target.md:219` lists
`skills/charter-workflow` among what the DSH build consumes, and `:233` copies it
into the stage. The deprecation was never withdrawn, so the repository currently
generates a package from a tree its own design record schedules for deletion.

## Build order is significant

Run the builders in this order after any core change:

```text
python scripts/build_codex_plugin.py     # writes plugins/charter-kit/ and root skills/
python scripts/build_zcode_plugin.py     # independent of the other two
python scripts/build_dsh_plugin.py       # reads root skills/, so it must run last
python scripts/validate_kit.py .
```

Running `build_dsh_plugin.py` before `build_codex_plugin.py` packages the
previous revision of the skill into `plugins/dsh-charter-kit/`. `validate_kit.py`
catches the result, but only after the fact.

## Which copy do I edit?

| Change | Edit | Then run |
| --- | --- | --- |
| Charter text | `DEVELOPMENT_CHARTER.md` and the three `*/skills/charter-workflow/references/DEVELOPMENT_CHARTER.md` copies under `skills/`, `targets/codex/`, `targets/zcode/` | all three builders, then the validator |
| `SKILL.md` | `skills/charter-workflow/SKILL.md`, `targets/codex/skills/charter-workflow/SKILL.md`, `targets/zcode/skills/charter-workflow/SKILL.md` | all three builders, then the validator |
| Templates, prompts, command, references | `portable/…` and the mirrored copy under each `skills/charter-workflow/` tree | all three builders, then the validator |
| Dependency manifest or scripts | root `dependencies.json` / `scripts/*.py` and the copy inside each of the three skill trees | all three builders, then the validator |
| Codex manifest | `targets/codex/.codex-plugin/plugin.json` | `build_codex_plugin.py` |
| ZCode manifest or command | `targets/zcode/…` | `build_zcode_plugin.py` |
| DSH adapter code | `targets/dsh/…` | `build_dsh_plugin.py` |
| Anything under `plugins/` | nothing — regenerate | the owning builder |
| Root `.codex-plugin/plugin.json` | nothing — it is written back by the Codex builder | `build_codex_plugin.py` |

Root `skills/charter-workflow/` appears in the table above as an edit target
because `MIRRORS` and the tree comparisons still require it to match, and because
DSH reads it. Edit it *together with* `targets/codex/skills/charter-workflow/`
and rebuild in order; never edit it alone.

## How the validator reports drift

`scripts/validate_kit.py` compares the copies pairwise and reports
`{right}: differs from {left} ({label}; byte mismatch)`. The comparisons are:

| Label | Left (cited as reference) | Right (blamed) |
| --- | --- | --- |
| `target/core mirror` | root `skills/charter-workflow` (generated) | `targets/codex/skills/charter-workflow` (hand-edited) |
| `generated distribution mirror` | `targets/codex/skills/charter-workflow` | `plugins/charter-kit/skills/charter-workflow` |
| `legacy distribution mirror` | root `skills/charter-workflow` (generated) | `plugins/charter-kit/skills/charter-workflow` |
| `ZCode distribution skill mirror` | root `skills/charter-workflow/SKILL.md` (generated) | `plugins/zcode-charter-kit/skills/charter-workflow/SKILL.md` |
| `distribution mirror` | root core files and `portable/` | the same paths under `plugins/charter-kit/` |
| `DSH target/distribution …` | `targets/dsh/…` | `plugins/dsh-charter-kit/…` |
| `ZCode target/distribution …` | `targets/zcode/…` | `plugins/zcode-charter-kit/…` |

Three of those rows cite a generated tree as the reference, so the message reads
as if root `skills/` were authoritative. Those comparisons now append an explicit
`hand-edit <path>` hint naming the tree to open instead. The
`ZCode distribution skill mirror` row is also indirect: the ZCode builder reads
`targets/zcode/skills/charter-workflow/`, but nothing compares that tree to root
`skills/` directly — an edit there is caught only once the ZCode plugin is
rebuilt, and the plugin is blamed rather than the target.

## Known inconsistencies to resolve

These are recorded, not fixed, by this file:

1. DSH consumes a tree the design record deprecates. Either repoint
   `build_dsh_plugin.py` at a hand-edited source, or withdraw the deprecation in
   the design record and describe root `skills/` as a supported generated tree.
2. `build_codex_plugin.py --check` reports PASS while its own writeback
   destination is stale, because `ensure_check_match` does not compare it.
